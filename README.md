# リアルタイムビンゴ

忘年会・結婚式二次会・社内イベント向けのリアルタイム・ビンゴWebアプリ。
参加者はスマホで URL を開くだけ、主催者は PC から抽選、会場のスクリーンには投影画面を映す——という 3 画面構成です。

- **依存パッケージなし**（Node.js 20+ だけで動作。`npm install` 不要。QR 生成ライブラリは同梱）
- **QR コード・短縮URL・ポスター印刷**で大人数に一斉共有。5,000 人同時接続を実測済み
- リアルタイム同期は Server-Sent Events（SSE）。切断時は自動再接続し、全状態を再送
- ビンゴ判定は**必ずサーバー側で検証**（カード・抽選はすべてサーバーが生成・保持）

## 起動

```bash
npm start          # http://localhost:3000
PORT=8080 npm start
npm test           # ロジック + API/SSE の統合テスト
```

状態は `data/rooms.json` に自動保存され、サーバー再起動後もゲームを再開できます（`DATA_FILE` で保存先を変更可）。

## 参加者への共有（URL・QR）

ルームを作るとホスト画面に **QR コード・短縮URL（`/r/ルームコード`）・ルームコード** が表示されます。

| 共有方法 | 使いどころ |
| --- | --- |
| 投影画面（`/screen`）の QR | 開始前は QR を画面いっぱいに表示。入場しながらスマホで読み取ってもらう |
| 🖨 ポスター印刷（`/poster`） | A4 の参加用ポスター。受付・各テーブル・入口に貼る |
| 📤 共有 / LINEで送る / 📋 コピー | 事前に Slack・LINE グループ・メールで参加URLを配る |
| ルームコード（5文字） | QR が読めない人向け。トップページで入力 |

QR から開いた人には、イベント名と「ニックネーム入力欄」だけのシンプルな参加画面が出ます（ルームコード入力や主催者メニューは表示しません）。一度参加した端末は、同じ QR を読むと自分のカードにそのまま戻れます。

### 共有URLはどこを指すか

| 状況 | 共有URL |
| --- | --- |
| `PUBLIC_URL` を設定（本番推奨） | `PUBLIC_URL/r/XXXXX` |
| 公開サーバーのドメインでホスト画面を開いた | そのドメイン |
| ホストが `localhost` で開いている | 自動で **LAN の IP**（例 `http://192.168.1.10:3000`）に切替え、警告を表示。同じ Wi-Fi の端末だけが参加可能 |

## 大規模会場での運用

### 実測値（`npm run loadtest`、同一マシン上で計測）

| 同時接続 | 参加処理 | 抽選結果が全員に届くまで（p95 / 最大） |
| --- | --- | --- |
| 3,000 人 | 2.1 秒 | 0.09 秒 / 0.18 秒 |
| 5,000 人 | 3.9 秒 | 0.20 秒 / 0.35 秒 |

抽選演出（1.4 秒）より十分短いので、会場全体で同時に番号が表示されます。本番環境で事前に確認する場合は:

```bash
npm run loadtest -- https://your-bingo.example.com 2000 5   # URL 人数 抽選回数
```

### 大人数向けの工夫

- 参加・マス開けなど**個人の操作は本人とホストにだけ**配信（全員に配ると N² 通になるため）。ホスト・投影画面への更新は 0.5 秒ごとにまとめて送信
- 配信データの共通部分は 1 回だけ JSON 化し、個人部分だけ連結
- 参加者認証はトークン索引で O(1)
- 切断時の再接続待ち時間を 1.5〜5 秒でランダム化（Wi-Fi 瞬断後の一斉再接続を分散）
- 会場 Wi-Fi は全員が同じグローバル IP になりやすいため、参加のレート制限は IP あたり 6,000 回/分（`JOIN_RATE_PER_MIN` で変更可）
- 1 ルームの上限は 5,000 人

### 当日のチェックリスト

1. **公開サーバーにデプロイ**して `PUBLIC_URL` を設定（下記）。会場 Wi-Fi が不安定でも 4G/5G から参加できる
2. HTTPS を有効化（参加トークンを暗号化するため。多くの PaaS は自動）
3. リバースプロキシを使う場合は SSE のバッファリングを無効化し、タイムアウトを長めに（`X-Accel-Buffering: no` は送出済み）
4. サーバーのファイルディスクリプタ上限を人数×1.2 以上に（`ulimit -n`）
5. 前日に `npm run loadtest` で想定人数を試す
6. ポスターを印刷し、投影画面は開始前から QR を映しておく

## デプロイ

```bash
docker build -t bingo .
docker run -p 3000:3000 -e PUBLIC_URL=https://bingo.example.com -v bingo-data:/data bingo
```

Render・Fly.io・Railway・Cloud Run など Docker が動く PaaS ならそのまま動きます（Cloud Run は最小インスタンス 1・リクエストタイムアウト最大に設定）。ゲーム状態はメモリと `/data/rooms.json` にあるため、**インスタンスは 1 台**で運用してください。

| 環境変数 | 既定値 | 内容 |
| --- | --- | --- |
| `PORT` | 3000 | 待ち受けポート |
| `PUBLIC_URL` | なし | 参加URL・QR に使う公開URL |
| `DATA_FILE` | `data/rooms.json` | 状態の保存先 |
| `JOIN_RATE_PER_MIN` | 6000 | 1 IP あたりの参加受付上限（毎分） |

## 画面

| URL | 利用者 | 内容 |
| --- | --- | --- |
| `/` | 全員 | ルーム作成（主催者）／ルームコード＋ニックネームで参加 |
| `/play?room=XXXXX` | 参加者 | ビンゴカード、マス開け、リーチ・ビンゴ表示、ビンゴ申請、出目履歴、当選者一覧 |
| `/host?room=XXXXX` | 主催者 | 抽選、開始/一時停止/再開/終了/リセット、当選者管理、タイブレーク、設定、参加者一覧 |
| `/screen?room=XXXXX` | プロジェクター | 大きな抽選演出、1〜75 の出目ボード、当選者と景品、参加用 QR（開始前は大きく表示） |
| `/poster?room=XXXXX` | 受付・テーブル | 印刷用の参加ポスター（QR・URL・手順） |
| `/r/XXXXX` | 参加者 | QR に入っている短縮URL（参加画面へ転送） |

## 要件との対応

### 1. 機能要件

| 要件 | 実装 |
| --- | --- |
| カード生成・配付 | B:1-15 / I:16-30 / N:31-45 / G:46-60 / O:61-75 の標準形式、中央 FREE。ルーム内で**重複しないカード**を保証。1人 1〜4 枚を設定可能 |
| マス目のチェック | 出た番号のマスをタップで開ける（未抽選の番号はサーバーが拒否）。誤タップは再タップで取り消し |
| 自動チェック | 参加者ごとに ON/OFF。主催者が「自動マス開け」自体を禁止することも可能 |
| リーチ判定 | あと 1 マスの箇所を点滅表示＋「リーチ！」バナー＋バイブレーション |
| ビンゴ判定 | 揃った列をハイライト、カードが光る、申請成功時に紙吹雪エフェクト |
| ビンゴ申請 | ボタン一つで申請 → サーバー検証 → ホスト・投影画面・全参加者にリアルタイム通知 |
| 番号抽選 | 1〜75 を重複なしで暗号学的乱数（`crypto.randomInt`）により抽出 |
| 抽選アニメーション | ドラムロール風の演出（全クライアントで同じ長さ）。演出が終わるまでカードに反映しないのでネタバレなし |
| 出目履歴 | 参加者画面に直近の履歴、ホスト・投影画面に 1〜75 のボード |
| 当選者管理 | 名前・順位・成立球数・景品をリアルタイム表示 |
| ゲームコントロール | 開始・一時停止・再開・終了・リセット（全員のカードを配り直して再ゲーム） |

### 2. 非機能要件

| 要件 | 実装 |
| --- | --- |
| リアルタイム性 | SSE で全員に同時配信。5,000 人同時接続で抽選結果が最大 0.35 秒以内に全員へ到達（下記「大規模会場での運用」） |
| 不正防止 | カード・マーク・抽選履歴はサーバーのみが保持。申請時は「マークが抽選済み番号だけか」「成立条件を満たすか」「抽選履歴上で本当に成立しているか」を三重チェック。ホスト操作はトークン認証（定数時間比較）。誤/不正申請はホスト画面でカウント |
| マルチデバイス | スマホ・タブレット・PC・プロジェクターでレスポンシブ表示 |
| セッション維持 | 参加トークンを端末に保存。リロード・通信断でも同じカードと開けたマスが復元。サーバー再起動後も `data/rooms.json` から復元 |

### 3. イベント・運営要件

| 要件 | 実装 |
| --- | --- |
| 成立条件 | 1列（縦・横・斜め）／十字／四隅／全開け。公平性のため開始後は変更不可 |
| 景品 | 1行1つで登録 → ビンゴ順位に自動で紐付け、投影画面にも表示 |
| 同時ビンゴ | 「何球目で成立したか」をサーバーが算出し、同じ球で成立した人を**同時ビンゴ**として自動検出。くじ引き（ランダム）／残りリーチ数が多い順／手動（じゃんけん結果を ↑↓ で反映）で決定 |
| 投影環境 | `/screen` をプロジェクターで全画面表示 |
| 制限時間・テンポ | 自動抽選（N 秒ごと）と制限時間（到達で自動終了）。経過/残り時間を全画面に表示。ホストは Space キーで抽選 |

## 構成

```
server.js          HTTP サーバー・REST API・SSE 配信
src/game.js        純粋なゲームロジック（カード生成、判定、成立球数、順位）
src/rooms.js       ルーム状態・権限・永続化・自動抽選タイマー
src/vendor/        QR コード生成（qrcode-generator, MIT, Kazuhiko Arase）
scripts/loadtest.js 負荷試験
public/            フロントエンド（素の HTML/CSS/ES Modules）
test/              node:test によるテスト
```

### API（抜粋）

| メソッド | パス | 認証 |
| --- | --- | --- |
| POST | `/api/rooms` | なし（ホストトークンを返す） |
| POST | `/api/rooms/:id/join` | なし（参加トークンを返す） |
| GET | `/api/rooms/:id/events?token=` | 任意（ホスト/参加者/投影で配信内容が変わる） |
| POST | `/api/rooms/:id/mark` `/claim` `/prefs` | 参加トークン（`X-Token`） |
| POST | `/api/rooms/:id/host/{start,pause,resume,draw,finish,reset,settings,tiebreak,move}` | ホストトークン（`X-Token`） |

## さらに大規模にする場合

1 ルーム 5,000 人・単一プロセスが現在の設計上限です。1 万人を超える場合は、状態を Redis 等に移して複数プロセス化し、Pub/Sub で配信する構成に変更してください。
